# TutorPulse

TutorPulse is a learning-outcomes and intervention service for tutors.

It provides a REST API for recording anonymised assessment results, monitoring topic-level performance and documenting support interventions. The project uses synthetic demonstration data and must not contain identifiable pupil information.

## Current functionality

The API currently supports:

- Creating, viewing, updating and deleting anonymised learners
- Creating, viewing, updating and deleting curriculum topics
- Creating, viewing, updating and deleting assessments
- Recording and managing topic-level assessment results
- Recording and managing learner interventions
- Validating names, titles, scores and intervention states
- Returning clear HTTP status codes and error responses
- Interactive API documentation generated by FastAPI
- Automated unit and isolated API tests
- PostgreSQL integration tests covering constraints, relationships and transactions
- Real API integration tests using PostgreSQL
- Docker Compose support for running FastAPI and PostgreSQL together
- Continuous integration through GitHub Actions

## Privacy

Only fictional, synthetic or fully anonymised learner data may be used.

Do not add real pupil names, contact details, school identifiers or other personal information to the database, source code, tests, screenshots or repository history.

## Local setup

The following instructions use Windows PowerShell.

### 1. Clone the repository

```powershell
git clone https://github.com/OmarUddin06/tutorpulse.git
cd tutorpulse
```

### 2. Create a virtual environment

```powershell
py -m venv .venv
```

If PowerShell blocks activation scripts, temporarily allow them in the current PowerShell window:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

Activate the environment:

```powershell
.\.venv\Scripts\Activate.ps1
```

The PowerShell prompt should begin with `(.venv)`.

### 3. Install the Python dependencies

```powershell
python -m pip install --upgrade pip
```

```powershell
python -m pip install -r requirements.txt
```

The main dependencies include:

- FastAPI for the web API
- SQLAlchemy for database access
- Psycopg for the PostgreSQL connection
- Pydantic and Pydantic Settings for validation and configuration
- pytest for automated testing
- HTTPX2 for FastAPI test clients

### 4. Create the local PostgreSQL database

```powershell
createdb -U postgres -h localhost -p 5432 tutorpulse
```

PostgreSQL will request the password for the local `postgres` user.

### 5. Create the database tables

```powershell
psql -U postgres -h localhost -p 5432 -d tutorpulse -v ON_ERROR_STOP=1 -f database/migrations/001_create_initial_schema.sql
```

### 6. Add the synthetic demonstration data

```powershell
psql -U postgres -h localhost -p 5432 -d tutorpulse -v ON_ERROR_STOP=1 -f database/seed.sql
```

### 7. Configure the database connection

Copy the example configuration:

```powershell
Copy-Item .env.example .env
```

Open `.env` and replace the password placeholder with the password for the local PostgreSQL `postgres` user:

```text
TUTORPULSE_DB_HOST=localhost
TUTORPULSE_DB_PORT=5432
TUTORPULSE_DB_NAME=tutorpulse
TUTORPULSE_DB_USER=postgres
TUTORPULSE_DB_PASSWORD=your-local-postgres-password
```

The `.env` file is ignored by Git. Never commit database passwords or other secrets.

## Run the API locally

Ensure the virtual environment is active, then run:

```powershell
python -m uvicorn app.main:app --reload
```

The API will be available at:

```text
http://127.0.0.1:8000
```

Use the interactive FastAPI documentation at:

```text
http://127.0.0.1:8000/docs
```

The OpenAPI specification is available at:

```text
http://127.0.0.1:8000/openapi.json
```

Stop the development server by pressing `Ctrl + C`.

## Run with Docker Compose

Docker Compose provides an alternative to running FastAPI and PostgreSQL directly on the host computer.

It creates:

- A PostgreSQL database container
- A FastAPI application container
- A private Docker network connecting the services
- A persistent Docker volume for the database data
- Health checks for both services

### 1. Create the Docker environment file

```powershell
Copy-Item .env.docker.example .env.docker
```

Open `.env.docker` and replace its password placeholder with a local Docker database password.

The `.env.docker` file is ignored by Git and must not be committed.

### 2. Build and start the services

```powershell
docker compose --env-file .env.docker up --build --detach
```

The first build may take longer because Docker must download the required base images and install the Python dependencies.

### 3. Check the service status

```powershell
docker compose --env-file .env.docker ps
```

The database and API should both become healthy.

The API is available at:

- API: `http://127.0.0.1:8000`
- Interactive documentation: `http://127.0.0.1:8000/docs`
- Health check: `http://127.0.0.1:8000/health`

The containerised PostgreSQL database is exposed to the host on port `5434`.

### 4. Test the health endpoint

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health
```

### 5. View the container logs

```powershell
docker compose --env-file .env.docker logs
```

Follow new log messages until `Ctrl + C` is pressed:

```powershell
docker compose --env-file .env.docker logs --follow
```

### 6. Stop the services

```powershell
docker compose --env-file .env.docker down
```

This removes the containers and Docker network but preserves the database volume.

To also remove the Docker database volume and its synthetic data:

```powershell
docker compose --env-file .env.docker down --volumes
```

The `--volumes` option permanently removes only the database volume belonging to this Docker Compose project. Its synthetic data can be recreated from the migration and seed files.

## Automated testing

TutorPulse contains two complementary categories of automated tests:

- Unit and isolated API tests that run without connecting to PostgreSQL
- Integration tests that use a real PostgreSQL test database

### Isolated tests

Run only the tests that do not require PostgreSQL:

```powershell
python -m pytest -m "not integration" -v
```

Expected result:

```text
57 passed
```

These tests cover:

- API health
- Request validation
- CRUD behaviour
- HTTP status codes
- Missing records
- Duplicate values
- Score validation
- Intervention state rules

### PostgreSQL integration-test setup

The integration tests use a separate `tutorpulse_test` database on port `5433`.

They must never use the main `tutorpulse` development database.

Create the ignored test configuration file:

```powershell
Copy-Item .env.test.example .env.test
```

Open `.env.test` and replace the password placeholder with the password that will be used by the test database container.

Create the test database container:

```powershell
docker run --name tutorpulse-test-db --env POSTGRES_DB=tutorpulse_test --env POSTGRES_USER=postgres --env POSTGRES_PASSWORD=tutorpulse_test_password --publish 127.0.0.1:5433:5432 --volume tutorpulse-test-db-data:/var/lib/postgresql --detach postgres:18.6
```

The example command uses `tutorpulse_test_password`. The password in `.env.test` must match the password supplied to the Docker container.

Check that PostgreSQL is ready:

```powershell
docker exec tutorpulse-test-db pg_isready -U postgres -d tutorpulse_test
```

Expected output includes:

```text
accepting connections
```

Copy the migration into the container:

```powershell
docker cp .\database\migrations\001_create_initial_schema.sql tutorpulse-test-db:/tmp/001_create_initial_schema.sql
```

Apply the migration:

```powershell
docker exec tutorpulse-test-db psql -U postgres -d tutorpulse_test -v ON_ERROR_STOP=1 -f /tmp/001_create_initial_schema.sql
```

### Integration tests

Run only the PostgreSQL integration tests:

```powershell
python -m pytest tests/integration -v
```

Expected result:

```text
18 passed
```

The integration tests verify:

- Connection to the dedicated test database
- Presence of the expected database tables
- PostgreSQL check constraints
- Unique constraints
- Foreign-key constraints
- Cascade deletion
- Restricted deletion
- Setting nullable foreign keys to `NULL`
- Transaction rollback and test isolation
- FastAPI routes using a real PostgreSQL database

Some integration tests deliberately attempt invalid database operations. PostgreSQL may record constraint errors in its service logs while those tests are running. These messages are expected when the related tests pass.

### Complete test suite

Run every test:

```powershell
python -m pytest -v
```

Expected result:

```text
75 passed
```

Stop the test database when it is no longer needed:

```powershell
docker stop tutorpulse-test-db
```

Start the existing test container again later:

```powershell
docker start tutorpulse-test-db
```

## Continuous integration

The GitHub Actions repository check runs automatically for every push and pull request.

The workflow:

1. Checks out the repository.
2. Starts a PostgreSQL 18.6 service.
3. Sets up Python 3.14.
4. Installs the project dependencies.
5. Applies the database migration.
6. Compiles the application and test files.
7. Runs all 75 automated tests.
8. Validates the Docker Compose configuration.
9. Builds the TutorPulse Docker image.

A pull request should only be merged after the repository check completes successfully.

The PostgreSQL service logs may contain expected constraint errors caused by integration tests that deliberately submit invalid data. The overall GitHub Actions result must still be successful.

## Initial user stories

### Record an anonymised learner

As a tutor, I want to create an anonymised learner record so that I can monitor progress without storing unnecessary personal information.

### Record an assessment result

As a tutor, I want to record an assessment result against an assessment and topic so that I can track a learner’s performance over time.

### Review topic-level progress

As a tutor, I want to view a learner’s results by topic so that I can identify areas where additional support may be beneficial.
