# TutorPulse Model Evaluation

## Purpose

This document explains how TutorPulse's learner-support classification models were trained, compared, evaluated and interpreted.

The modelling task is to predict whether a learner's next assessment result will fall below the agreed support threshold, using only information that would have been available before that assessment took place.

The project uses entirely synthetic learner data. The results demonstrate a reproducible machine-learning workflow, but they must not be treated as evidence about real learners or used to make real educational decisions.

## Modelling question

> Using only a learner's assessment history available before a future assessment, can TutorPulse predict whether their next assessment result will fall below an agreed support threshold?

A result is classified as requiring support when:

```text
assessment percentage < 60%
```

This creates a binary classification target:

- `1`: the result is below 60% and may require support
- `0`: the result is at least 60%

The model predicts risk rather than making an educational decision. A tutor would still need to interpret the prediction alongside wider educational context.

## Data source

The modelling data is generated by:

```text
analysis/synthetic_data.py
```

The synthetic data follows the structure of the TutorPulse PostgreSQL database:

- learners
- topics
- assessments
- assessment results
- interventions

The generated records are fictional and reproducible. A fixed random seed allows the same source data to be regenerated consistently.

The leakage-safe modelling dataset is created by:

```text
analysis/modelling_dataset.py
```

Generated and prepared datasets are excluded from Git because they are reproducible build outputs.

## Unit of prediction

Each modelling row represents one learner-topic result for a target assessment.

For each row:

- the target is the learner's percentage score on that assessment and topic
- the model only receives historical information dated before the target assessment
- the learner ID, assessment ID and other record identifiers are retained only as metadata
- identifiers are not supplied to the model as predictive features

## Leakage prevention

Data leakage occurs when a model receives information that would not have been available at prediction time.

TutorPulse prevents leakage by constructing every historical feature from records strictly earlier than the target assessment date.

The following information is prohibited from the model feature matrix:

- the target score
- the target percentage
- the binary target label
- identifiers used only to locate records
- information created on or after the target assessment
- future interventions or assessment results

Automated tests verify the expected feature contract and reject prohibited columns.

## Feature groups

The model uses 18 approved features drawn from several groups.

### Assessment context

These describe the upcoming assessment without revealing its result:

- topic
- maximum possible score

### Overall assessment history

These summarise results that existed before the target assessment:

- number of previous assessments
- number of previous results
- average historical percentage
- minimum historical percentage
- maximum historical percentage
- number of previous below-threshold results
- historical support rate
- average percentage on the immediately preceding assessment
- days since the previous assessment

### Topic-specific history

These describe the learner's earlier performance in the same topic:

- number of previous same-topic results
- average previous same-topic percentage
- latest previous same-topic percentage

### Intervention history

These count interventions created before the target assessment:

- total previous interventions
- completed previous interventions
- previous interventions for the same topic

Missing historical values are handled inside the trained modelling pipeline rather than being filled using future data.

## Chronological data split

The dataset is divided chronologically instead of randomly.

| Split | Rows | Date range | Support rate |
|---|---:|---|---:|
| Training | 5,668 | 29 January 2025 to 16 July 2025 | 37.2% |
| Validation | 2,168 | 30 July 2025 to 24 September 2025 | 30.0% |
| Test | 2,220 | 8 October 2025 to 3 December 2025 | 26.5% |

The average amount of learner history increases over time:

| Split | Mean previous results | Median previous results |
|---|---:|---:|
| Training | 25.795 | 24 |
| Validation | 58.531 | 60 |
| Test | 76.663 | 76 |

This shift is important because later predictions are made for learners with longer recorded histories.

The splits serve different purposes:

- **Training:** fit model parameters.
- **Validation:** compare models and select the decision threshold.
- **Test:** perform one final assessment of the selected approach.

The chronological design is closer to the intended use of predicting future outcomes from past information.

## Preprocessing pipeline

The preprocessing and classifier are contained in a single scikit-learn pipeline.

The pipeline:

1. selects the approved model features
2. imputes missing numerical values
3. scales numerical features
4. imputes missing categorical values
5. one-hot encodes categorical features
6. passes the transformed data to the classifier

Keeping preprocessing and classification together ensures the same transformations are applied during training, evaluation and later inference.

## Models evaluated

Three model types were evaluated.

### Dummy baseline

The dummy classifier predicts the majority class.

It provides a minimum performance reference. A trained model should offer meaningful improvement over this baseline.

### Logistic regression

Logistic regression was selected as the final model.

Advantages include:

- probabilistic risk estimates
- strong validation performance
- relatively straightforward interpretation
- deterministic and reproducible training
- a smaller risk of overfitting than more complex alternatives

### Random forest

A random forest was included as the required tree-based comparison.

It can learn nonlinear relationships and interactions, but it is more complex and less directly interpretable than logistic regression.

## Evaluation metrics

Accuracy alone is not sufficient because most results do not fall below the support threshold.

The evaluation therefore includes:

- **Precision:** among predictions marked as requiring support, how many actually required support?
- **Recall:** among results that required support, how many did the model identify?
- **F1 score:** the harmonic mean of precision and recall.
- **Balanced accuracy:** the average of performance on the positive and negative classes.
- **ROC AUC:** how well the model ranks positive cases above negative cases across thresholds.
- **Average precision:** precision-recall performance across thresholds.
- **Brier score:** the mean squared error of predicted probabilities; lower is better.
- **Specificity:** the proportion of non-support cases correctly identified.
- **Confusion matrix counts:** true negatives, false positives, false negatives and true positives.

Recall is particularly important because a false negative means a learner who may require support was not flagged.

Precision must still remain reasonable so that tutors are not overwhelmed by false alerts.

## Validation threshold selection

A probability of 0.50 is the common default decision threshold, but it is not automatically appropriate for every problem.

TutorPulse selects the threshold using validation data only.

The selection rule prioritises recall while requiring precision of at least:

```text
0.60
```

The chosen threshold is:

```text
0.38
```

Lowering the threshold from 0.50 to 0.38 increases the number of learners identified for possible support.

### Logistic regression at the default threshold

| Metric | Validation result |
|---|---:|
| Accuracy | 0.814 |
| Balanced accuracy | 0.795 |
| Precision | 0.669 |
| Recall | 0.750 |
| F1 score | 0.707 |
| ROC AUC | 0.873 |
| Average precision | 0.758 |
| False negatives | 163 |
| False positives | 241 |

### Logistic regression at the selected threshold

| Metric | Validation result |
|---|---:|
| Accuracy | 0.782 |
| Balanced accuracy | 0.791 |
| Precision | 0.602 |
| Recall | 0.811 |
| F1 score | 0.691 |
| ROC AUC | 0.873 |
| Average precision | 0.758 |
| Brier score | 0.134 |
| False negatives | 123 |
| False positives | 349 |

The selected threshold reduces false negatives from 163 to 123, at the cost of increasing false positives from 241 to 349.

That trade-off is deliberate: TutorPulse prioritises identifying more potentially at-risk results while maintaining validation precision of at least 60%.

## Development-order disclosure

During development, the logistic-regression test evaluation was implemented before the tree-model comparison was completed.

This is not the ideal experimental sequence because the test split should remain untouched until every model-selection decision has been finalised.

The limitation was handled as follows:

- the tree model was compared using validation data
- the threshold was not changed after viewing the test results
- no model parameters were tuned against the test results
- the final choice remained logistic regression based on validation performance, probability quality, reproducibility and interpretability
- the limitation is recorded here rather than hidden

For future modelling work, every candidate model should be implemented and compared before the test evaluation is run.

## Model interpretation

Logistic-regression coefficients describe associations learned from the synthetic training data.

They do not demonstrate that a feature causes a learner to need support.

### Strongest associations with higher predicted support odds

| Feature | Coefficient | Odds ratio |
|---|---:|---:|
| Fractions topic | 0.978 | 2.660 |
| Algebra topic | 0.272 | 1.313 |
| Latest same-topic percentage | 0.209 | 1.233 |
| Completed intervention count | 0.108 | 1.114 |
| Previous support count | 0.106 | 1.112 |
| Same-topic intervention count | 0.076 | 1.079 |
| Maximum score | 0.056 | 1.057 |
| Minimum historical percentage | 0.029 | 1.029 |

### Strongest associations with lower predicted support odds

| Feature | Coefficient | Odds ratio |
|---|---:|---:|
| Average historical percentage | -1.852 | 0.157 |
| Statistics topic | -1.005 | 0.366 |
| Geometry topic | -0.527 | 0.590 |
| Previous-assessment average | -0.347 | 0.707 |
| Previous intervention count | -0.207 | 0.813 |
| Same-topic average percentage | -0.088 | 0.916 |
| Historical support rate | -0.087 | 0.917 |
| Maximum historical percentage | -0.068 | 0.935 |

Some signs may appear counterintuitive. For example, latest same-topic percentage has a positive coefficient after the model accounts for several correlated historical-performance features.

A coefficient represents the feature's conditional association while the other transformed features remain fixed. It must not be read as a simple standalone rule.

## Distribution shift

The support rate decreases across the chronological periods:

- training: 37.2%
- validation: 30.0%
- test: 26.5%

The amount of available learner history also increases substantially over time.

These changes demonstrate temporal distribution shift. The model retained useful ranking and recall performance, but the reduction in test precision shows that operational performance can change as the data distribution changes.

A deployed system would require:

- continuing performance monitoring
- periodic threshold review
- checks for changes in topic distribution
- checks for changes in support prevalence
- checks for probability calibration
- retraining criteria
- human review of model-assisted decisions

## Responsible-use limitations

The current modelling work has several important limitations:

- all learner records are synthetic
- the generated patterns may not represent real educational behaviour
- no sensitive demographic features are available
- subgroup analysis is limited to operational groups
- the model predicts a score-derived label rather than a verified support need
- a low assessment result does not automatically explain why support is needed
- model predictions can contain both false positives and false negatives
- logistic-regression coefficients are associations rather than causal effects
- the selected threshold reflects a project-specific trade-off
- later real-world data may have different distributions
- the test split was accessed earlier than ideal during development

TutorPulse predictions should therefore be treated as decision-support signals, never as automatic decisions.

## Conclusion

The selected logistic-regression pipeline provides a reproducible and interpretable improvement over the majority-class baseline.

At the fixed test threshold of 0.38, it achieved:

- 79.5% accuracy
- 79.6% balanced accuracy
- 58.3% precision
- 79.8% recall
- 0.884 ROC AUC
- 0.744 average precision

The model identified most below-threshold results while producing a meaningful number of false alerts. This supports its use as a demonstration of tutor-facing decision support, provided its limitations, synthetic-data basis and need for human judgement remain explicit.
